# GUI interactive capability ledger

Parity tracker for `@bastani/atomic-gui`. **Do not claim parity from fake-engine unit tests alone.**

| Column | Meaning |
|---|---|
| Capability | Interactive user-facing capability |
| GUI route / exclusion | Native control, slash command, shortcut, or deliberate exclusion |
| Evidence | Test file, source, or walkthrough |
| Class | `fake` · `unit` · `real-engine` · `e2e` · `manual` · `docs` |
| Status | `proven` · `partial` · `open` · `excluded` |

**Parity rule:** a capability may be marked practical-parity only when it has a `real-engine` or `e2e` evidence row (plus any required manual OS walkthrough). `fake` / pure `unit` rows prove host structure only.

Required credentialed/OS/provider walkthroughs are listed in
[desktop-acceptance.md](desktop-acceptance.md). An unchecked item is an open
acceptance gate, not parity evidence.

## Phase 3 exit review (2026-08-11)

Phase 3 settings/theme/model/onboarding review preserves protocol v3 and engine authority. The GUI receives an engine-owned resolved theme snapshot with global→project precedence, validates and persists theme mutations through the engine, and never reads generic settings/theme paths. Scoped models are parsed from `get_available_models` and displayed in the model picker. Existing settings controls route through engine RPCs (`set_thinking_level`, steering/follow-up modes, auto compaction/retry).

Remaining exact boundaries: protocol v3 has no arbitrary settings-document or configured theme-path/resource mutation, and no live theme reload event. The first-run panel is renderer-host guidance into existing trust/auth/model routes; it does not prove real-provider login or model availability.
